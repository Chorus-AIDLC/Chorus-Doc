[Pi 编码智能体](https://pi.dev)是 Chorus 的官方集成，以已发布的 npm 包 **`@chorus-aidlc/chorus-pi`**
形式分发。它通过 Pi 原生的扩展、技能和智能体机制，提供 Chorus 工作流技能、只读评审子智能体、
Pi 官方的 `subagent` 工具，以及会话感知的扩展钩子，只需一条 `pi install` 即可安装。

Pi 还可以作为**可唤醒的 `--agent pi` 后台服务后端**运行：有工作被远程发给 Pi 时，Chorus 后台服务会唤醒一个
无头 Pi 会话，因此 Pi 能像 Claude Code、Codex 和 Kiro 一样参与反向对话循环。

安装前，请按照[为智能体创建访问权限](/zh/guides/administrator-setup/)创建一个智能体密钥。

## 前置条件

- 已安装 `pi` CLI（参见 [pi.dev](https://pi.dev)）。
- `pi-mcp-adapter` 包（唯一的运行时依赖），用于把 Chorus 的 `chorus_*` MCP 工具暴露给 Pi（Pi 没有
  原生 MCP）：
  ```bash
  pi install npm:pi-mcp-adapter
  ```
  **无需**安装单独的子智能体包，`chorus-pi` 自身已捆绑 Pi 官方的 `subagent` 工具。
- 一个 Chorus **API 密钥**（以 `cho_` 开头）。

## 步骤 1：导出环境变量

```bash
export CHORUS_URL="http://localhost:8637"
export CHORUS_API_KEY="cho_REDACTED"
```

把它们添加到 `~/.bashrc` / `~/.zshrc`，以便 Pi 在启动时读取。`CHORUS_URL` 可以是根 URL，也可以是完整
的 `/api/mcp` 端点。如果未设置，扩展会回退到从 `.mcp.json` 读取 `chorus` 服务器条目。

## 步骤 2：配置 MCP 服务器

Pi 的 `pi-mcp-adapter` 会自动发现标准 MCP 配置文件。在项目根目录放置一个 `.mcp.json`（或全局的
`~/.pi/agent/mcp.json`），让主智能体获得 `chorus_*` 工具：

```json
{
  "mcpServers": {
    "chorus": {
      "type": "http",
      "url": "http://localhost:8637/api/mcp",
      "headers": { "Authorization": "Bearer cho_REDACTED" }
    }
  }
}
```

直接写入 URL 和 Bearer 即可使用，Pi 不需要在 `.mcp.json` 中展开 `${VAR}`。由于 `.mcp.json`
包含智能体密钥，请不要将其提交到版本控制。

## 步骤 3：安装 chorus-pi 包

```bash
pi install npm:@chorus-aidlc/chorus-pi
```

这就是全部安装步骤。`subagent` 工具随包内置，三个评审智能体直接从包自带的 `agents/` 目录中发现，
既**无需**单独的子智能体依赖，也**无需**手动把智能体文件复制到 `~/.pi/agent/agents/`。重启 Pi
（`/reload` 或开启新会话），以便加载扩展、技能和评审智能体。

在本地开发 `chorus-pi`？改从仓库检出安装：`pi install ./packages/chorus-pi`。

## 验证连接

重启 Pi，查看 `/mcp`，并请求 Pi 调用 `chorus_checkin`。确认返回结果显示预期的智能体身份和权限，并且
首个回合报告了包含你签到信息的 `# Chorus Plugin — Active` 上下文。输入 `/skill:chorus` 确认技能已加载，
并在 `/subagents` 中查看是否有 `chorus-proposal-reviewer`。

## 能力

- **14 个技能**，驱动每个 AI-DLC 阶段：`/skill:chorus`、`/skill:idea`、`/skill:proposal`、
  `/skill:develop`、`/skill:review`、`/skill:quick-dev`、`/skill:yolo`、`/skill:brainstorm`、
  `/skill:orchestrate`、`/skill:docs`、`/skill:chorus-cli`，外加 `openspec-aware`、`spec-lite` 与 `research` 子流程。
  `research` 是想法与提案技能调用的简短事实调研流程，也是想法的[**调研**操作](/zh/guides/capture-an-idea/#在开发之前请求调研)所运行的流程。
- **3 个只读评审子智能体**：`chorus-proposal-reviewer`、`chorus-task-reviewer`、
  `chorus-code-reviewer`，从包内目录发现（无需复制），通过 `subagent` 工具派生；
  它们发布一条 `VERDICT` 评论后停止。使用社区的 `pi-subagents` 包时，调用中直接点名的 Chorus 评审
  子智能体和 worker 一律在后台运行（即使调用要求 `async: false`），因为该包的前台子进程无法访问 Chorus 工具。
- **Pi 官方的 `subagent` 工具**，内置于 `extensions/subagent/`（Pi 的参考实现），无需任何第三方
  子智能体包。它同时**与社区的 `pi-subagents` 包（nicobailon）共存**：两者都注册名为 `subagent`
  的工具，因此需通过 `settings.packages` 过滤器排除内置的那一个；`chorus-pi` 的会话生命周期既支持
  该包的**异步 / detached** subagent 运行，也支持内置的阻塞式运行。过滤器与配置详见
  [`chorus-pi` README](https://www.npmjs.com/package/@chorus-aidlc/chorus-pi)。
- **会话感知扩展**，订阅 Pi 的原生事件（`session_start` → `chorus_checkin` + 规格模式解析，
  `subagent` 上的 `tool_call` → 每个 worker 的 Chorus 会话，`tool_result` → 关闭 worker 会话 + 评审
  提示，`session_shutdown` → 清理）。

该扩展通过环境变量配置（Pi 没有插件设置界面）。`CHORUS_SPEC_MODE` 可指定 `openspec`、`lite` 或
`off`；未指定时，优先使用可用的 OpenSpec，否则使用 spec-lite。旧的 `CHORUS_OPENSPEC_MODE=off`
只禁用 OpenSpec，回退结果是 `lite` 而非自由格式。不想生成本地规格文件时，请设 `CHORUS_SPEC_MODE=off`。
详见 [OpenSpec 模式](/zh/guides/openspec-mode/)与 [Spec-lite 模式](/zh/guides/spec-lite-mode/)。
评审开关仍是 `CHORUS_ENABLE_{PROPOSAL,TASK,CODE}_REVIEWER`（默认 `true`）。

## 将 Pi 作为可唤醒的后台服务后端运行

Pi 是完整支持的**可唤醒后台服务后端**，有工作被远程发给它时（分配给你的智能体的想法/任务、
一次 @提及、一个提案决策），Chorus 后台服务会唤醒一个无头 Pi 会话。

最简单的方式是 `chorus agents add`：在智能体清单中选择 **Pi**，它会通过 `pi install` 安装
`pi-mcp-adapter` 与 `chorus-pi`，在 `~/.chorus/daemon.json` 中把 Pi 登记为**可唤醒**
智能体，并且（如果你选择启用）安装开机唤醒它的后台服务。若要手动配置，请以 Pi 后端运行后台服务：

```bash
chorus daemon --agent pi
```

- 后台服务从 `PATH` 解析 `pi` 可执行文件（可用 `CHORUS_PI_PATH` 覆盖），每次唤醒启动一个无头的
  `pi --mode rpc` 进程，并把 `CHORUS_URL` / `CHORUS_API_KEY` / `CHORUS_AGENT_PROFILE` 导出到被唤醒
  的会话中。后台唤醒需要 **Pi 0.85.0 或更新版本**，详见 [0.20.0 的 daemon 行为](#0200-的-daemon-行为)。
- Pi **没有权限系统**，因此不涉及沙箱 / 跳过权限的标志，`chorus` 与 `yolo` 两种后台服务模式运行
  Pi 的方式完全一致。
- 被唤醒的 Pi 只能通过本包的扩展 / `pi-mcp-adapter` 访问 Chorus MCP 工具，因此请在后台服务唤醒的环境
  中保持安装 `chorus-pi`（从 npm 安装可确保后台服务能用到它）。

后台服务提供 Chorus 连接（`CHORUS_URL`、`CHORUS_API_KEY` 和 `CHORUS_AGENT_PROFILE`），但不会
替你获取模型提供方凭据。可通过 `~/.chorus/daemon.json` 中该智能体的 `env` 提供，也可使用后台服务继承的环境或
提供方支持的凭据存储。`systemd --user` 服务不会继承登录 shell 中导出的变量。[管理后台服务](/zh/guides/daemon-operations/)
说明了模型与思考参数、每智能体 env、服务凭据和重启要求。

### 0.20.0 的 daemon 行为

从 Chorus 0.20.0 起，每次 Pi 唤醒都通过 Pi 的 RPC 模式运行，不再回退到之前的无头模式。因此请在每台运行
后台服务的主机上升级 Pi：

```bash
pi --version                                                # 需要 0.85.0 或更新版本
npm install -g @earendil-works/pi-coding-agent@latest       # 升级 pi 本身
```

`chorus upgrade --plugins` 会更新 `chorus-pi` 和 `pi-mcp-adapter`，但不会升级 Pi 本身。该行为已在
Linux 上用 Pi **0.85.1** 实测验证。

- **Pi 版本过旧**：后台服务会跳过这次唤醒，并在日志中给出上面的升级命令。如果读取不到 Pi 版本，
  后台服务会记录警告并照常尝试唤醒。
- **会话连续性**：每个想法保留自己的 Pi 会话，升级前创建的会话也一样。如果 Pi 无法恢复之前会话的
  历史，唤醒会在新会话中继续，对话中会显示一条提示，说明之前的历史无法恢复。
- **打断**：在 Chorus 中点击**打断**会通过 RPC `abort` 停止 Pi 当前的运行（包括正在执行的工具）；即使 Pi 进程以退出码 0 结束，该轮仍记录为
  已中断。如果 `sigintTimeoutMs` 到期时 Pi 仍在运行，后台服务会像以前一样强制停止它。
- **扩展对话框**：唤醒期间没有人在终端前，因此扩展弹出的对话框（select、confirm、input 或
  editor）会被立即取消，后台服务日志记录 `cancelled pi extension <method> dialog`。请改用 Chorus
  评论或需求细化提问。
- **查找进程**：Pi 会把进程名改为 `pi`，所以在 Linux 上 `pgrep -f 'pi --mode rpc'` 找不到它。请使用
  `pgrep -x pi -P <daemon-pid>`。

## 常见问题

- **找不到 MCP 服务器：** 把 `.mcp.json` 放在项目根目录（或 `~/.pi/agent/mcp.json`），或运行
  `/mcp setup`。
- **技能未加载：** 重启会话（`/reload`），技能在会话启动时加载。
- **评审智能体不可用：** 确认已安装 `chorus-pi` 且已重启 Pi；评审智能体随包内置（无需单独安装子
  智能体，也无需手动复制）。
- **连接未授权：** 重新检查 `CHORUS_URL` / `CHORUS_API_KEY`（或 `.mcp.json` 中的 Bearer），然后重启 Pi。
- **工具名看起来重复了**（`chorus_chorus_checkin`）：`pi-mcp-adapter` 在网关模式下会给工具名加上服务器
  名前缀。可调用 `mcp({ tool: "chorus_chorus_checkin" })`，或在 chorus 服务器上设置
  `"toolPrefix": "none"` 以使用原生的 `chorus_*` 名称。

关于一般的连接问题，参见[排查智能体连接故障](/zh/guides/troubleshooting/)。
