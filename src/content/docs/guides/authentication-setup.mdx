Most of Chorus is workspace-scoped, but one role sits above the workspaces: the **Super
Admin**. It is how you create workspaces and turn on single sign-on (SSO) for your team.
This guide is for whoever runs the Chorus deployment; end users who just need to sign in
should read [Account and workspace](/guides/account-and-workspace/).

## Enable the Super Admin

The Super Admin is a platform-level account, separate from any workspace. You enable it on
the server with two environment variables — the admin email and a bcrypt hash of the admin
password:

```sh
SUPER_ADMIN_EMAIL="admin@example.com"
SUPER_ADMIN_PASSWORD_HASH="$2b$10$..."   # bcrypt hash of your password
```

Generate the hash with a one-off command, for example:

```sh
node -e "console.log(require('bcryptjs').hashSync('your-password', 10))"
```

Keep the bcrypt hash in your deployment's secret store. Admin sessions also need a secure
`NEXTAUTH_SECRET`: for a single instance, the npm `chorus` launcher and the Docker entrypoint
can generate and persist it for you. With more than one replica, set the same value
explicitly on all of them. See [Docker session secrets](/guides/deploy-docker/#session-secret-nextauth_secret).

## Sign in as Super Admin

There is no link to the admin panel inside the app — you reach it through the normal
sign-in screen. Enter the Super Admin email; Chorus recognizes it and asks for the admin
password on a dedicated step, then opens the **Super Admin** panel. The admin session is
independent of any workspace and is shorter-lived than a normal session, so you sign in
again periodically.

:::caution[The Super Admin has no workspace boundary]
Unlike a workspace admin agent, the Super Admin is not scoped to one workspace — it manages
the whole deployment. Treat its credentials accordingly. A workspace **admin agent** (see
[Manage agents](/guides/manage-agents/)) governs work *inside* a single workspace; the
Super Admin governs the *workspaces themselves*.
:::

## Create a workspace

In the Super Admin panel, **Companies** lists every workspace with its email domains, OIDC
status, and user and agent counts. Use it to create, edit, and delete a workspace.

When you create one, you give it a **name**, one or more **email domains**, and its SSO
settings (below). The email domains are what let a person's email find this workspace at
sign-in.

:::caution[Deleting a workspace is permanent]
Deleting a workspace removes it and all of its data — projects, ideas, proposals, tasks,
documents, agents, and users. There is no undo.
:::

## Configure SSO (OIDC)

Chorus signs users in through your identity provider using OpenID Connect with PKCE — there
is **no client secret** to manage. You configure it per workspace, in that workspace's
settings in the Super Admin panel, under **OIDC Configuration**. Two values are required:

- **OIDC Issuer URL** — your provider's OpenID Connect discovery URL.
- **Client ID** — the application's client ID from your provider.

SSO turns on automatically once both are set; clearing either turns it off. Chorus requests
the standard `openid profile email` scopes.

At your identity provider, register Chorus as an application and add its **redirect
(callback) URL** to the allowed list: your Chorus site's address followed by
`/login/callback`. The Companies list shows the exact URL to copy. Because it is built from
the address you used to open Chorus, open the Companies page from your production URL and
copy the value shown there.

### How this reaches your users

Once a workspace has SSO configured, a person signing in with an email on one of its
domains is sent to your identity provider and back — the flow described in
[Account and workspace](/guides/account-and-workspace/). A user whose email matches more
than one SSO workspace is asked to pick one. Someone already added to a workspace is signed
in to it even if their email domain differs.
