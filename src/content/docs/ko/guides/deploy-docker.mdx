Chorus는 공식 Docker 이미지 `chorusaidlc/chorus-app`을 제공합니다. 이 가이드는 두 가지 Compose 형태(스탠드얼론(내장 데이터베이스)과 프로덕션(외부 PostgreSQL + Redis)), 기존 데이터베이스에 연결하는 순수 `docker run`, 전체 환경 변수 참고, 그리고 컨테이너가 시작 시 무엇을 하는지 보여 줍니다.

먼저 이미지를 풀합니다.

```bash
docker pull chorusaidlc/chorus-app:latest
```

스탠드얼론 형태와 프로덕션 형태 중 무엇을 고를지는 [배포 개요](/ko/guides/deployment-overview/)를 참고하세요.

## 스탠드얼론(내장 데이터베이스)

외부 데이터베이스가 필요 없습니다. 이미지는 [PGlite](https://pglite.dev)(내장 PostgreSQL)를 함께 담고 있으며 모든 것을 자동으로 시작합니다. 데이터는 Docker 볼륨에 저장되어 컨테이너 재시작을 넘어 유지됩니다.

`docker-compose.local.yml`을 만듭니다.

```yaml
# Standalone Chorus — embedded PGlite, no external PostgreSQL or Redis
services:
  app:
    image: chorusaidlc/chorus-app:latest
    ports:
      - "8637:8637"
    environment:
      # No DATABASE_URL — entrypoint auto-starts embedded PGlite
      - REDIS_URL=
      # Leave empty: the container generates a random session secret on first
      # start and keeps it in the chorus-local-data volume. Set it explicitly
      # (openssl rand -base64 32) if you prefer to manage it yourself.
      - NEXTAUTH_SECRET=${NEXTAUTH_SECRET:-}
      - COOKIE_SECURE=false
      - DEFAULT_USER=${DEFAULT_USER:-admin@example.com}
      - DEFAULT_PASSWORD=${DEFAULT_PASSWORD:-changeme}
    volumes:
      - chorus-local-data:/app/data

volumes:
  chorus-local-data:
```

그런 다음 실행합니다.

```bash
docker compose -f docker-compose.local.yml up -d
```

`http://localhost:8637`을 열고 `admin@example.com` / `changeme`로 로그인합니다(또는 `DEFAULT_USER` / `DEFAULT_PASSWORD` 환경 변수로 재정의합니다).

스탠드얼론 모드에서 컨테이너는 다음을 수행합니다.

- PGlite를 내부 포트(`5433`)에서 시작하며, 외부로 노출하지 않습니다.
- 데이터를 `chorus-local-data` Docker 볼륨에 저장하므로 재시작을 넘어 유지됩니다.
- `NEXTAUTH_SECRET`을 비워 두면 첫 시작 시 무작위 세션 서명 비밀 키를 생성해 같은 볼륨에 저장합니다([세션 비밀 키](#세션-비밀-키nextauth_secret) 참고).
- Redis를 비활성화합니다(메모리 내 EventBus로 폴백 — 단일 인스턴스만).
- 시작 시 Prisma 마이그레이션을 자동으로 실행합니다.

## 프로덕션(외부 PostgreSQL + Redis)

프로덕션 환경, 특히 다중 복제본을 둘 때는 앱을 외부 PostgreSQL과 Redis에 연결하세요. `docker-compose.yml`을 만듭니다.

```yaml
services:
  app:
    image: chorusaidlc/chorus-app:latest
    ports:
      - "8637:8637"
    environment:
      - DATABASE_URL=postgresql://chorus:chorus@db:5432/chorus
      - REDIS_URL=redis://default:chorus-redis@redis:6379
      # Session-signing secret. Leave empty and the container generates one on
      # first start and persists it in the chorus-app-data volume (single
      # replica only). For production, or more than one app container, set it
      # explicitly in .env or the environment:  openssl rand -base64 32
      # Changing the secret logs every user out.
      - NEXTAUTH_SECRET=${NEXTAUTH_SECRET:-}
      - DEFAULT_USER=admin@example.com
      - DEFAULT_PASSWORD=your-password
    volumes:
      - chorus-app-data:/app/data
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy

  redis:
    image: redis:7-alpine
    command: redis-server --requirepass chorus-redis
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "-a", "chorus-redis", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: chorus
      POSTGRES_PASSWORD: chorus
      POSTGRES_DB: chorus
    volumes:
      - chorus-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U chorus -d chorus"]
      interval: 5s
      timeout: 5s
      retries: 5

volumes:
  chorus-app-data:
  chorus-data:
  redis-data:
```

그런 다음 실행합니다.

```bash
docker compose up -d
```

세션 비밀 키를 직접 제공하려면 compose 파일과 같은 위치의 `.env`에 적어 둡니다.

```bash
echo "NEXTAUTH_SECRET=$(openssl rand -base64 32)" >> .env
```

`http://localhost:8637`을 열고 `DEFAULT_USER` / `DEFAULT_PASSWORD`에 설정한 자격 증명으로 로그인합니다.

:::caution[HTTPS와 보안 쿠키]
위의 Compose 파일은 HTTP 전용 배포(예: 내부 네트워크 테스트)를 지원하기 위해 `COOKIE_SECURE=false`를 설정합니다. `COOKIE_SECURE=false`는 신뢰할 수 있는 내부 네트워크에서만 사용하세요. 이 경우 쿠키가 암호화되지 않은 HTTP로 전송됩니다. 프로덕션에서 HTTPS 뒤에 배포할 때는 보안 쿠키를 켜기 위해 `COOKIE_SECURE=true`를 설정하세요.
:::

## 기존 PostgreSQL에 연결해 실행하기

이미 PostgreSQL과 Redis가 실행 중이라면 컨테이너를 직접 시작합니다.

```bash
docker run -d \
  -p 8637:8637 \
  -e DATABASE_URL=postgresql://user:pass@your-db-host:5432/chorus \
  -e REDIS_URL=redis://default:password@your-redis-host:6379 \
  -e NEXTAUTH_SECRET="$(openssl rand -base64 32)" \
  -e COOKIE_SECURE=false \
  -e DEFAULT_USER=admin@example.com \
  -e DEFAULT_PASSWORD=your-password \
  chorusaidlc/chorus-app:latest
```

비밀 키는 한 번만 생성하고 이후 시작에서는 같은 값을 재사용하세요. 시작할 때마다 새 값을 쓰면 모든 사용자가 로그아웃됩니다. `NEXTAUTH_SECRET`을 생략하는 경우, 자동 생성된 비밀 키가 컨테이너 재생성 후에도 남도록 `/app/data`에 볼륨을 마운트하세요(`-v chorus-app-data:/app/data`).

## 시작 시 동작

컨테이너의 엔트리포인트는 시작할 때마다 같은 순서를 실행합니다.

1. `NEXTAUTH_SECRET`을 확인합니다. 비어 있거나 이전 예제 파일에 있던 자리 표시자 값이면, 컨테이너는 `/app/data/.secret`에서 비밀 키를 읽거나 새로 생성하고 무엇을 했는지 로그에 남깁니다(값 자체는 절대 출력하지 않습니다). 직접 명시적으로 설정한 비밀 키는 그대로 사용됩니다.
2. `DATABASE_URL`이 설정되지 않고 `DB_*` 변수도 하나도 제공되지 않으면, 엔트리포인트는 내부 포트(`5433`)에서 내장 PGlite 인스턴스를 시작합니다. 외부 데이터베이스가 **구성되어 있으면** PGlite는 시작하지 않습니다.
3. `prisma migrate deploy`를 실행해 보류 중인 데이터베이스 마이그레이션을 적용합니다.
4. 데이터베이스가 아직 준비되지 않았으면 10초마다 재시도합니다(최대 30회, 약 5분).
5. 마이그레이션이 성공하면 Next.js 서버가 `8637` 포트에서 시작합니다.

:::note[마이그레이션은 자동으로 실행됩니다]
마이그레이션을 직접 실행할 필요가 없습니다. 보류 중인 마이그레이션을 시작 시 적용하는 것은 엔트리포인트의 일부이므로, 업그레이드는 같은 데이터베이스에 대해 새 이미지를 시작하는 것뿐입니다. 새 이미지는 첫 부팅 때 스키마를 마이그레이션할 수 있으므로, 업그레이드 전에 데이터베이스나 데이터 볼륨을 백업하세요. [운영](/ko/guides/deploy-operations/)을 참고하세요.
:::

## 세션 비밀 키(`NEXTAUTH_SECRET`)

`NEXTAUTH_SECRET`은 일반 사용자와 슈퍼 관리자를 모두 포함해 Chorus의 모든 세션 쿠키에 서명합니다. 이 값을 아는 사람은 누구나 비밀번호 없이 어떤 계정으로든 유효한 세션을 만들 수 있으므로, 공개된 적이 있는 값을 절대 사용하면 안 됩니다.

:::caution[0.18.0 이하에서 업그레이드하는 경우]
이전 예제 Compose 파일은 `NEXTAUTH_SECRET`이 설정되지 않았을 때 공개된 기본값을 채워 넣었습니다. 0.18.1부터 컨테이너는 이러한 알려진 자리 표시자 값의 사용을 거부하고 대신 실제 비밀 키를 생성합니다. 따라서 0.18.1에서의 첫 시작은 새 비밀 키를 발급하며 **모든 사용자가 한 번 다시 로그인해야 합니다**. `app` 서비스에 `/app/data` 볼륨이 없는 **오래된** compose 파일로 프로덕션 형태를 실행하는 경우, 컨테이너를 재생성할 때마다 비밀 키가 다시 생성되어 위의 볼륨을 추가하거나 `NEXTAUTH_SECRET`을 명시적으로 설정할 때까지 업그레이드마다 사용자가 로그아웃됩니다.
:::

### 컨테이너의 동작

<div class="table-scroll" role="region" aria-label="시작 시 NEXTAUTH_SECRET 처리" tabindex="0">

  | 시작 시의 `NEXTAUTH_SECRET` | 동작 |
  | --- | --- |
  | 직접 설정한 값 | 그대로 사용합니다. 디스크를 읽거나 쓰지 않습니다. |
  | 비어 있음 | `/app/data/.secret`에 값이 있으면 재사용하고, 없으면 64자 무작위 비밀 키를 생성해 소유자만 읽을 수 있는 권한으로 저장하며, 로그에 `generated a new random secret` 또는 `reusing the persisted secret`을 남깁니다. |
  | 이전의 공개 자리 표시자 중 하나 | 비어 있는 것과 똑같이 처리하고, 이유를 설명하는 `WARNING` 줄을 로그에 남깁니다. |

</div>

컨테이너는 비밀 키를 출력하지 않으며 공개된 값으로 폴백하지도 않습니다. 비밀 키 파일을 읽거나 쓸 수 없으면 컨테이너는 마이그레이션을 실행하기 전에 오류로 중지합니다. 또한 Docker에 한정되지 않고 어떤 배포 방식에서든, 시작 시 공개 자리 표시자가 여전히 사용 중이면 애플리케이션이 `error` 수준의 `security` 로그를 기록합니다.

### `/app/data`를 볼륨에 두기

생성된 비밀 키는 `/app/data/.secret`에 있으므로 `/app/data`는 영구 볼륨이어야 합니다. 이 페이지의 두 Compose 예제는 모두 볼륨을 마운트합니다(`chorus-local-data`, `chorus-app-data`). 볼륨이 없으면 컨테이너 재생성이나 이미지 업그레이드마다 새 비밀 키가 만들어져 모든 사용자가 로그아웃됩니다. 비밀 키를 생성하거나 재사용할 때마다 시작 로그가 이 점을 알려 줍니다.

### 앱 컨테이너를 여러 개 실행하기

자동 생성은 **단일** 앱 컨테이너를 위한 것입니다. 레플리카가 여러 개이면 각 레플리카가 서로 다른 비밀 키를 갖게 되어, 요청이 다른 레플리카에 도달할 때마다 세션이 실패합니다. 배포 계층(Compose `.env`, Kubernetes Secret, ECS 태스크 정의)에서 모든 레플리카에 **같은** `NEXTAUTH_SECRET`을 명시적으로 설정하세요. [AWS CDK 배포](/ko/guides/deploy-production/)는 AWS Secrets Manager를 통해 이미 이렇게 하고 있습니다.

### 비밀 키 설정과 교체

값을 한 번 생성해 명시적으로 설정합니다.

```bash
openssl rand -base64 32
```

compose 파일 옆의 `.env`에 넣거나, `docker run`에 `-e`로 전달하거나, 시크릿 저장소에서 주입하세요. 명시적 값이 항상 우선하며 자동 생성을 비활성화합니다. 비밀 키를 교체하면(의도적으로 바꾸든 `/app/data/.secret`을 삭제하든) 기존 세션이 모두 무효화되어 슈퍼 관리자를 포함한 모든 사용자가 다시 로그인해야 합니다.
